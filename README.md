# The Ontology Imperative (TOI)

Reference artifacts for governing agentic AI.

The Ontology Imperative (TOI) argues that agentic AI requires a governed Meaning Layer as preventive governance infrastructure, owned by the Chief Data Officer before execution, rather than detective controls bolted on afterwards. Values are claimed; architecture is enforced. The mandate that follows spans four sovereignties: semantic, the meanings the enterprise commits to; enforcement, the constraints that must hold at runtime; execution, the agents permitted to act; and, beneath those three, jurisdictional, the ground the platform itself answers to.

This repository is the canonical home of the reference artifacts that operationalise that argument. Each one answers a single question, serves a defined audience, and is built to travel on its own while cross-referencing the others. The series itself is published at [theontologyimperative.substack.com](https://theontologyimperative.substack.com), and the branded library front door is at [fredericverhelst.com/toi-library](https://fredericverhelst.com/toi-library).

## How to use them

The Capability Stack defines what an organisation must own and govern. The Readiness Assessment and the Use Case Risk Classification Framework are diagnostic: they locate where the organisation stands and how exposed a given use case is. The CDO Mandate and the Board Briefing carry the governance and boardroom case, and the CDO Role Specification sets out who can hold the mandate. The Vendor Coverage Diagnostic supports procurement and architecture decisions. The Board Pack assembles the board-facing artifacts into a single document for distribution.

These are descriptive and diagnostic instruments. They do not set the maturity thresholds that gate deployment for any specific organisation. Those thresholds are organisation-specific, sector-specific, and regulatory-context-specific, and remain an internal governance decision taken with legal counsel. No published framework can substitute for that decision.

## Versioning and provenance

Each artifact carries its own version and date on the page. That label is the provenance record: it identifies the exact copy you are holding. It is not, however, what the artifacts cite when they reference one another. Cross-references name the major line only (the Capability Stack as v3, for instance) or name the artifact without a number, so that a minor revision to one artifact does not ripple through every artifact that points to it. The single exception is an assessment pinned to a specific state: the Vendor Coverage Diagnostic is assessed against a specific Stack version, and there the exact version and date are cited. The authoritative copy of every artifact lives here and on the library page; the current version of each, with its changelog, is on the [Releases](../../releases) page.
